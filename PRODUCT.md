# ShapePilot

Approachable AI-assisted 2D/3D design, viewing, editing, and fabrication.

## What this is

ShapePilot is a standalone design and fabrication workbench. Wave 1 ships one
complete capability — the **Keycap Tray Designer** — extracted with exact
behaviour and data parity from the Hearth monolith, on its own runtime, its own
identity boundary and its own database.

A person opens ShapePilot to lay out keycap pockets in a tray, check whether the
result can actually be printed or cut, and export a file their machine accepts.
Everything downstream of that — geometry, validation, STL/3MF/SVG/DXF — happens
in the browser. Nothing about a design is uploaded except its parameters.

## Who it is for

One household maker with a Bambu X2D printer and a Shaper Origin CNC, working
on Systainer inserts and similar organisers. Every design belongs to the signed-in
account and is visible only to that account.

## Durable constraints

These hold regardless of what the product grows into.

- **The model is millimetres, y-up.** Imperial display is a formatting layer;
  nothing is stored in inches.
- **Fabrication output is generated client-side and is not persisted.** The
  server stores design parameters. Generated bytes are reproducible from them.
- **Manufacturability is advisory and per machine.** A design that is invalid on
  the CNC may be perfectly fine on the printer. Nothing is silently corrected.
- **The mesh must be watertight.** A slicer that "repairs" a leaky mesh distorts
  the pockets. Non-manifold output is an error, not a warning.
- **One account owns a design.** `(tenant_id, oid)` is the only authorization
  key. Email and display name are for humans to read, never for the server to
  trust.
- **One process, one database file.** SQLite is the authority; there is no
  second writer and no scale-out.
- **Production data is never mutated by a tool in this repository.** Legacy
  import reads an immutable, hash-verified backup and writes only into
  ShapePilot's own database.

## Deliberately deferred

Named here so that their absence is a decision rather than an oversight.

- Importing STL or SVG for viewing and editing, and a UI for authoring custom
  tray profiles. Custom profile data already loads and exports; nothing creates
  it yet.
- Original freeform 2D/3D modelling beyond the keycap tray.
- Machine, material and tooling profiles beyond the current fabrication fields.
- The AI design copilot. When it arrives it proposes typed, previewable,
  undoable modelling commands — it does not edit the document directly.
- Server-side geometry, persisted generated artifacts, collaboration,
  multi-instance operation, and PostgreSQL.
- Azure provisioning, image build and deployment, and the production cutover.
- Blob-backed design assets. The artifact-store boundary exists now; the Blob
  adapter arrives with the first feature that persists binary artifacts.

## Inherited semantics kept on purpose

Wave 1 preserves user outcomes before improving them. Two behaviours are carried
across unchanged and are tracked in `docs/PARITY_CHECKLIST.md`:

- Engraving depth, per-pocket depth and label mode are stored and round-trip,
  but nothing reads them yet.
- The `shape` and `mirror_x` pocket columns exist in the inherited schema and are
  preserved byte-for-byte on import, but the API contract does not carry them —
  exactly as in the source. An ISO Enter pocket therefore reloads as a
  rectangle. Changing that is a product decision, not a port decision.
